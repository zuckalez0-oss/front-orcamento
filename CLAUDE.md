# CLAUDE.md — GeoQuote (Lypsyos)

Fonte de verdade sobre arquitetura e decisões de projeto. Para instruções de setup/instalação, ver `README.md`.

## Stack

- **Backend**: FastAPI + SQLAlchemy 2.x + SQLite (`backend-orcamentos/geoquote.db`, arquivo local, não versionado). Modelos/rotas CRUD/motor de cálculo/DXF (`ezdxf`) em `main.py`; nesting 2D (`rectpack`) isolado em `nesting.py`; fórmulas de tempo/custo em `pricing.py`; geometria de formas padrão (R/Q/C/T) em `geometria.py`.
- **Frontend**: React 19 + Vite + Tailwind v4. Tela principal ainda é um componente único `front-orcamentos/src/App.jsx` (~1950 linhas, sem roteador — telas controladas por state: `formulario`, `parametrizacao`, `resultado`, `perfil`), mas parte da lógica já foi extraída pra módulos satélite conforme cresceu: `RapidEntryGrid.jsx` (Entrada Rápida em grade), `pecaUtils.js` (construção do objeto peça, compartilhado entre Formulário e Entrada Rápida), `nestingUtils.js` (funções puras de geometria/transformação compartilhadas entre a tela e o PDF), `nestingPdf.js` + `relatorioIndustrialPdf.js` (exportação do plano de corte em PDF, ver seção própria abaixo). Estilos utilitários Tailwind + um punhado de classes customizadas em `App.css`. PDF gerado com `jspdf` + `jspdf-autotable`.
- Não há autenticação de verdade além do que já existe via Supabase (RBAC simples ADMINISTRADOR x outros papéis, ver `useAuth.js`/`PerfilUsuario.jsx`) — é uma ferramenta interna de orçamento para máquinas de corte a laser/plasma/guilhotina.

## Rodando localmente

```bash
cd backend-orcamentos && source venv/bin/activate && uvicorn main:app --reload   # http://localhost:8000
cd front-orcamentos && npm run dev                                              # http://localhost:5173
```

## Schema do banco de dados

Três tabelas independentes, propositalmente separadas (ver "Decisões arquiteturais" abaixo):

- **`materiais`** (`MaterialDB`): `id, nome, espessura, precoKg, densidade`. Chave natural de upsert: `(nome, espessura)`.
- **`maquinas_params`** (`MaquinaParamDB`): `id, maquina, material, espessura, velocidadeCorte, tempoPiercing, tempoSetup, valorHora`. Chave natural de upsert: `(maquina, material, espessura)`. O campo `material` é um link "fraco" (string) para `materiais.nome` — não há FK real.
- **`perfis_tributarios`** (`PerfilTributarioDB`): `id, nome, imposto_perc`. Chave natural de upsert: `nome`.

Todas as rotas `POST /materiais`, `POST /maquinas-params`, `POST /perfis-tributarios` fazem upsert pela chave natural (busca por essa chave; se existe, atualiza; senão, cria). `Base.metadata.create_all()` roda no import do módulo, seguido de `seed_dados_iniciais()` — que só insere dados de exemplo se a tabela correspondente estiver vazia (idempotente, seguro rodar toda vez que o processo sobe).

As dimensões de chapa (`largura`/`comprimento`/`margem`/`offsetPeca`, e agora também `maquina` e `clienteQuerSobra` por espessura — ver seção Nesting) **não são persistidas**: são digitadas/marcadas no modal "Dimensões de Chapa" a cada orçamento e viajam no payload de `/calcular-orcamento`. Isso é intencional, mesmo padrão usado desde antes deste documento existir — chapa/margem/offset/máquina/sobra são tratados como parâmetros por-orçamento, não cadastro fixo.

## Decisões arquiteturais

- **Por que 3 tabelas de parâmetros em vez de uma:** o cadastro original misturava Preço/Kg (muda toda semana, é decisão de compras) com Velocidade/R$-hora (quase fixos, decisão de engenharia) num único registro por combinação máquina+material+espessura. Isso obrigava reeditar registro por registro sempre que o aço mudava de preço. Separar em Material (mercado) / Máquina-Corte (engenharia) / Perfil Tributário (faturamento) deixa cada tabela mudar no seu próprio ritmo. O join entre `materiais` e `maquinas_params` acontece no frontend (`parametroAtual` em `App.jsx`), não no backend.
- **Por que o dropdown de Espessura às vezes aparece vazio:** ele reflete apenas combinações Máquina+Material que já têm uma linha em `maquinas_params`. Cadastrar uma espessura só em `materiais` (aba Matéria-prima) não a torna selecionável até existir também o parâmetro de corte correspondente em `maquinas_params` (aba Máquina & Corte). O frontend avisa quando essa lacuna existe (ver aba "Máquina & Corte" e mensagens de estado vazio no formulário de peça).
- **Nesting é retangular na camada de bin-packing, não poligonal genérico:** a alocação de itens na chapa (`rectpack`) continua operando só sobre bounding boxes (mesmo quando a peça é importada de DXF — `nesting.py` só recebe `dimA`/`dimB`, nunca o contorno). NFP (No-Fit-Polygon) genérico — colisão polígono-a-polígono arbitrária, via Shapely/pyclipper — foi avaliado e descartado de novo por complexidade/tempo (é um projeto de pesquisa em si). **Exceção parcial, deliberada:** triângulos (`tipoPeca == 'T'`) têm identidades geométricas EXATAS de ladrilhamento — dois triângulos "reto" pareados ao longo da hipotenusa ladrilham um retângulo `base x altura` com 0% de desperdício; triângulos "isósceles" ladrilham em fileira alternada (apex-up/apex-down, passo `base/2`) com aproveitamento exato `N/(N+1)` para N peças na fileira. Esse pré-processamento (`nesting.py::_compor_itens_triangulo`) roda ANTES do `rectpack` e entrega blocos compostos já densos — é matemática fechada, não busca/heurística, então não reabre a questão do NFP genérico. Ver `backend-orcamentos/nesting.py`.
  - **Mas a RENDERIZAÇÃO de uma peça DXF já posicionada usa o contorno real**, não mais um retângulo genérico — isso é só desenho, não muda a decisão de bin-packing acima. Ver seção "Contorno real do DXF" abaixo.
- **Tema visual:** paleta definida em `App.css` (`--gq-dark-bg`, `--gq-navy-panel`, `--gq-orange-accent`, `--panel-gradient`) é o design system "oficial" da marca (laranja + preto). Historicamente só o header usava o tema escuro; a tela de inserção de peça foi migrada para usar `.panel-dark`/`.input-dark` (ver `App.css`) para ficar consistente com essa identidade. As telas "Parâmetros Globais" e "Resultado"/impressão permanecem no tema claro por enquanto.

## Motor de orçamento (`POST /calcular-orcamento`)

Recebe `cliente, imposto, comissao, margemLucro, frete, pecas[], configChapas{espessura: {largura, comprimento, margem, offsetPeca, maquina, clienteQuerSobra}}, incluiMaterial`. Para cada peça calcula tempo de corte (perímetro/velocidade + piercing por furo + movimento vazio por furo + setup único por espessura — ver `pricing.py::tempo_producao_unidade_min`, já considera nº de furos reais e não só o perímetro externo) e custo de material (peso × preço/kg). Agrupa por espessura, roda nesting real (`nestear_pecas` em `nesting.py`) para determinar quantas chapas são necessárias, e aplica markup/comissão/imposto sobre o custo de produção total. `imposto` chega pronto do frontend (já resolvido a partir do Perfil de Faturamento escolhido). Velocidade de corte/tempo de piercing já variam por máquina+material+espessura via `maquinas_params` — não é um valor fixo.

O campo `fatorNesting` do payload é herdado do modelo antigo (heurística área/eficiência) e não é mais usado — a contagem de chapas agora vem 100% do nesting real. Mantido no schema só para não quebrar o frontend; pode ser removido dos dois lados no futuro se ninguém mais depender dele.

Cada item de `detalhamento_espessuras` no retorno inclui, além dos totais de custo/tempo: `chapa_largura`, `chapa_comprimento`, `chapa_margem` (os valores efetivamente usados, já com fallback para 1200x3000/10mm se o frontend não mandou `configChapas` para aquela espessura), `maquina` (a que efetivamente foi usada no nesting — override de `configChapas[esp].maquina` ou, na ausência, a da primeira peça do grupo), `sobra_reservada_cliente` (bool, de `configChapas[esp].clienteQuerSobra`), métricas de **Controle de Sobras** (`chapa_area_total_mm2`, `kerf_perda_area_mm2`, `sucata_area_mm2`, `sucata_peso_kg`, `utilizacao_pct` — informativas; o custo de material já fatura a chapa inteira, então a sobra já está paga, isso não gera cobrança nova) e `nesting: {chapas_necessarias, chapas: [{placements: [{id, x, y, width, height, rotated, invertido}]}]}` — coordenadas já absolutas na chapa real (mm), prontas para desenhar sem transformação adicional no frontend. `totais_globais` tem os agregados equivalentes: `sucata_peso_total_kg`, `sucata_area_total_mm2`, `utilizacao_media_pct`, `custo_material`.

A resposta também traz `detalhamento_pecas` (dict indexado por `peca.id`, com `tempo_min`/`custo_maquina` **já calculados por peça individual** — não é rateio/estimativa, é o mesmo cálculo que já alimentava os agregados por espessura, só que exposto por peça) e `inclui_material` (eco do flag do payload). Usados na tabela impressa do orçamento (`App.jsx`, seção "TABELA DE PEÇAS - UNIFICADA") pra preencher as colunas Chapas/Tempo/Custo Máquina por linha, que antes ficavam sempre com "-".

**Facção x pacote completo (`incluiMaterial`):** checkbox no topo do formulário (`App.jsx`, estado `incluiMaterial`, default `true`). Quando `false`, o backend ainda calcula `chapas_necessarias`/`dimensao_chapa`/peso normalmente (informativo, pro orçamentista saber quanto material o cliente precisa trazer) mas **zera** `dados_esp["custo_material"]` e não soma em `custo_material_global` — o markup passa a incidir só sobre o custo de máquina/serviço. Refletido na UI como um selo "Pacote completo" / "Só serviço (facção)" no resumo e no cabeçalho do PDF impresso, e um card "Custo Material R$" nos totais (mostra R$ 0,00 quando é facção).

### Nesting (`backend-orcamentos/nesting.py`)

`nestear_pecas(pecas, largura_chapa, comprimento_chapa, margem, offset_peca, maquina=None)` — usa `rectpack` (`newPacker(rotation=True)`, multi-bin; `maquina == "GUILHOTINA"` troca o algoritmo de empacotamento, ver comentário no código). Peças não-triângulo (R/Q/C, e também DXF — ver seção abaixo) são expandidas em `qtd` retângulos individuais `(dimA + offset_peca) x (dimB + offset_peca)`, como sempre. Triângulos (`tipoPeca` em `pecas[i]`, precisa vir junto de `tipoTriangulo`) passam primeiro por `_compor_itens_triangulo`, que agrupa por `(tipoTriangulo, base, altura)` idênticos e devolve pares/fileiras compostos (ver decisão arquitetural acima) — só esses itens compostos (ou a sobra individual, se ímpar) chegam ao `packer.add_rect`. Depois do `packer.pack()`, um item composto é expandido de volta em N `placements` (um por triângulo membro), usando a mesma transformação de rotação 90° já usada para o item inteiro; cada placement de triângulo ganha `invertido: bool` (indica se o desenho deve usar o conjunto de vértices complementar — ver `verticesTriangulo` em `nestingUtils.js`). O padding (`offset_peca`) é subtraído de volta na posição final do item (par/fileira ou peça avulsa) para que o espaçamento visual entre itens seja exatamente `offset_peca` — mas NÃO existe padding entre os membros DENTRO de um item composto (eles interligam sem vão, por design). Levanta `NestingError` (capturada em `main.py` e convertida em `HTTPException 400`, nunca 500) quando: a margem é maior que a própria chapa, um item (peça avulsa ou par/fileira de triângulo) não cabe na área útil nem rotacionado, ou o total de itens pós-composição de uma espessura passa de `LIMITE_INSTANCIAS` (2000 — trava de segurança para não travar a API síncrona com lotes gigantes; pares/fileiras contam como 1 item cada, não pela contagem bruta de peças físicas). O frontend (`handleSalvar` em `App.jsx`) mostra o `detail` desse erro 400 direto num `alert()` e reabre o modal de configuração de chapa.

## Importação de DXF

- **Múltiplos arquivos de uma vez**: tanto o Formulário quanto a Entrada Rápida (`RapidEntryGrid.jsx`) aceitam selecionar vários `.dxf` de uma vez (`<input type="file" multiple>`). No Formulário, 1 arquivo popula o form pra revisão (fluxo antigo); 2+ arquivos importam cada um direto como peça própria (qtd=1, usando a máquina/material/espessura selecionados no momento), com resumo de sucesso/falha por arquivo. O identificador da peça vem do nome do arquivo (sem `.dxf`).
- **Importação por JSON**: botão próprio na Entrada Rápida (`RapidEntryGrid.jsx::parseJsonPecas`) — aceita um array de peças (ou `{"pecas": [...]}`) com campos `id/geometria/dimA/dimB/qtd/maquina/material/espessura` e furação (`tipoFuro/nFuros/diaFuro/furoOffsetX/furoOffsetY`). Mais expressivo que o CSV (que também existe, sem furação).
- **Edição em massa na Entrada Rápida** (`RapidEntryGrid.jsx`, estado `linhasSelecionadas`): cada linha ganhou um checkbox (+ um "selecionar todas" no cabeçalho). Hoje só o campo Máquina participa disso — se a linha que disparou o `onChange` faz parte de uma seleção com mais de 1 linha marcada, o novo valor se aplica a TODAS as linhas marcadas (cada uma recalculando seu próprio material/espessura padrão pra máquina nova, igual já acontecia numa edição de linha única). Ver `atualizarLinha`. Generalizável pra outros campos no futuro se pedirem — o mecanismo (`chavesAlvo` = seleção quando aplicável, senão só a linha corrente) já está pronto pra isso.
- **Contorno real do DXF**: `/processar-dxf` (`main.py`) extrai, além do `svgMarkup` (preview visual, mantido como estava) e das métricas de bounding box, um campo **aditivo** `contorno: {perfis: [{pontos: [[x,y],...], fechado}], furos: [{cx,cy,r}]}` — normalizado no referencial local `[0,dimA]x[0,dimB]`, origem no canto superior-esquerdo, mesma convenção já usada por `furosAbsolutos`/`verticesTriangulo` em `nestingUtils.js`. Só `LWPOLYLINE`/`POLYLINE`/`LINE`/`CIRCLE` são tratados (mesma limitação que o `svgMarkup` sempre teve); `ARC`/`SPLINE` não geram perfil — a peça cai de volta no retângulo da bounding box, sem quebrar nada.
  - Esse contorno **nunca vai pro backend em `/calcular-orcamento`** — vive só no objeto peça do frontend (`pecaUtils.js::construirPeca` grava em `contornoDxf`, restaurado em `editarPeca`/threading de import em lote/Entrada Rápida do mesmo jeito que `dxfPreviewSvg`). A renderização (tela `ChapaSVG` em `App.jsx` e PDF `nestingPdf.js`) já tem os placements com `id`, então busca a peça original em `listaPecas` e usa o contorno local dela — não precisa que o backend devolva nada a mais.
  - Transform de posicionamento (`nestingUtils.js::contornoDxfAbsoluto`): mesma identidade de rotação 90° usada pra furos/triângulos — `xAbs = rotated ? (dimB - y) : x; yAbs = rotated ? x : y`, depois translada por `placement.x/y`.
  - Heurística pra múltiplos perfis fechados (peça com rasgos internos desenhados como polilinha fechada, não só `CIRCLE`): o perfil de maior bounding box é o contorno EXTERNO (preenchido com a cor da peça); os demais fechados são "buracos" (preenchidos com o fundo, mesmo tratamento visual dos furos circulares); perfis abertos residuais só são traçados. Não é topologia CAD genérica, é uma simplificação pragmática — documentada assim no código (`nestingUtils.js::contornoDxfAbsoluto`, `nestingPdf.js`).
  - `furosAbsolutos` (`nestingUtils.js`) prefere os furos reais do DXF (`pecaOriginal.contornoDxf.furos`) quando existem, em vez da posição procedural calculada por `tipoFuro`/offsets (que é só aproximação pra peça desenhada à mão).

## PDF do Plano de Corte (nesting)

Layout reescrito num padrão "industrial" (inspirado num relatório de plano de corte real de outro sistema do setor — cabeçalho com logo/máquina/data, painel por espessura, plano de corte, especificações da chapa, lista de peças, sobras) pensado pra ser reutilizado por outras ferramentas de orçamento do nicho ferro/aço no futuro — por isso ficou em **dois módulos**:

- **`front-orcamentos/src/relatorioIndustrialPdf.js`** — o template genérico e reutilizável. Não conhece nada de "orçamento"/"peça"/"nesting" do GeoQuote, só desenha seções a partir de dados já resolvidos (texto/número simples), usando `jspdf-autotable` (dependência nova) pras tabelas com borda. Exporta uma função por seção (`desenharCabecalhoIndustrial`, `desenharPainelEspessura`, `desenharTituloPlanoDeCorte`/`desenharBarraTitulo`, `desenharTabelaEspecificacoesChapa`, `desenharTabelaPecasDoPlano`, `desenharTabelaSobras`, `desenharRodapeIndustrial`), cada uma recebendo `doc` + Y atual e devolvendo o próximo Y. Logo é um placeholder desenhado (`desenharLogoPlaceholder`) trocável em runtime via `configurarLogoRelatorio(dataUrlBase64)` sem mexer em mais nada.
- **`front-orcamentos/src/nestingPdf.js`** — o orquestrador GeoQuote-específico (mesma assinatura pública de antes: `gerarPdfNesting(resultadoOrcamento, listaPecas, cliente, espessuraFiltro, orientacao = 'retrato')`). Monta os dados e desenha o diagrama da chapa em si (que é nesting-específico: cores, contorno real, furos — reaproveita `nestingUtils.js`).

Pontos de design que valem lembrar antes de mexer aqui:

- **Chapas com arranjo idêntico viram 1 página só, com multiplicador "(NX)"** (`agruparChapasIdenticas`/`assinaturaChapa` em `nestingPdf.js`) — assinatura = lista ordenada de `(id, x, y, rotated)` por chapa; chapas com a mesma assinatura são o mesmo "Plano de Corte", só repetido N vezes fisicamente. Evita 1 página por chapa física quando o pedido tem muitas chapas repetidas. Cada título de plano também mostra a posição dentro do total de planos DAQUELA espessura, formato `(N-TOTAL)` — ex: espessura com 3 planos gera "PLANO DE CORTE 1 (1-3)", "...2 (2-3)", "...3 (3-3)" — ajuda o orçamentista a saber quantas páginas faltam sem contar manualmente (`desenharTituloPlanoDeCorte` em `relatorioIndustrialPdf.js`, parâmetro `totalPlanos`; combina com o `(MX)` de multiplicador quando os dois se aplicam).
- **Altura do diagrama é FIXA por orientação de página** (`ALTURA_DIAGRAMA_RETRATO_MM = 125`, `ALTURA_DIAGRAMA_PAISAGEM_MM = 85`), não calculada a partir do que sobra depois das tabelas — isso é proposital, garante que toda página de plano de corte tenha o mesmo tamanho de diagrama, independente de quantos tipos de peça ou sobras aparecem embaixo. Se as tabelas de peças/sobras não couberem no resto da página, o `autoTable` continua numa página seguinte com o cabeçalho de colunas repetido (`showHead: 'everyPage'` em `desenharTabelaPecasDoPlano`/`desenharTabelaSobras`) em vez de cortar a tabela sem contexto.
- **Diagrama sempre desenhado "deitado"**: quando `chapa_comprimento > chapa_largura` (chapa "em pé", ex: 1200x3000), o desenho inteiro é rotacionado 90° (`girar` em `desenharDiagramaChapa`, funções `pontoRotacionado90`/`retanguloRotacionado90`) — o eixo mais comprido sempre fica horizontal, porque a área do diagrama é sempre bem mais larga que alta (independente de a PÁGINA estar em retrato ou paisagem), então "deitar" a chapa aproveita muito melhor o espaço do que desenhar do jeito "natural". É só transformação de desenho — não mexe em `nesting.py`/nos placements reais.
- **Cota** (`desenharCotaChapa`): linha com marcas nas pontas embaixo (largura do desenho) e à direita (altura do desenho) da chapa, com a medida real em mm — não o valor escalado. O espaço reservado é MEDIDO de verdade (`medirReservaCotaVertical`, usa `doc.getTextWidth()` no texto real "NNNN mm" antes de calcular a escala), não um valor fixo chutado — já teve dois bugs em cima disso: (1) reserva fixa pequena demais fazia a chapa cobrir o número; (2) o texto da cota vertical era desenhado ROTACIONADO 90° (`angle:90`), o que se mostrou pouco confiável (saía sobreposto pela própria chapa em alguns casos, provavelmente por causa de como jsPDF ancora texto rotacionado) — trocado por texto HORIZONTAL normal ao lado da linha vertical, mais previsível e sempre legível.
- **`garantirEspaco(doc, y, alturaNecessariaMm, orientacaoPagina)`**: `desenharBarraTitulo` é desenho manual (não pagina sozinho); se vier logo antes de um `autoTable` que SIM pagina sozinho, dava pra a barra colar no rodapé da página e a tabela inteira (cabeçalho incluído) pular pra uma página nova quase em branco — bug real, já visto em produção. `garantirEspaco` checa ANTES de desenhar a barra se sobra altura suficiente pra ela + pelo menos 1 linha da tabela; se não sobrar, força a quebra de página primeiro, então barra+tabela sempre ficam juntas. Usado antes de "Lista Detalhada de Peças" e "Sobras" em `desenharPaginaDoPlano`, e antes de "Observações"/assinatura na página de orçamento.
- **Miniatura real na coluna "Imagem"** (`desenharThumbnailPeca` em `nestingPdf.js`, plugado via callback `renderizarImagem` em `desenharTabelaPecasDoPlano` — o template genérico não sabe desenhar peça, só oferece o gancho): desenha a peça "parada" (sem posição/rotação de chapa), reaproveitando `contornoDxfAbsoluto` com um placement identidade (`x=0,y=0,rotated=false`) pra reusar a mesma classificação externo/buraco sem duplicar lógica. Desenha também os FUROS por cima (reais do DXF quando existem, senão `calcularFuros` procedural) — já teve um bug onde a miniatura desenhava só o contorno e nunca os furos.
- **Tempo de corte por peça é RATEADO de verdade, não estimado**: cada linha de `desenharTabelaPecasDoPlano` mostra `tempo unitário da peça (detalhamento_pecas[id].tempo_min ÷ peca.qtd) × qtdNesting` (quantas unidades dela cabem NESSA chapa específica) — não é o tempo do orçamento inteiro. O "Tempo Corte" da tabela de especificações do plano (`desenharTabelaEspecificacoesChapa`) é a SOMA desses valores rateados de todas as peças do plano — não `item.tempo_min / chapas_necessarias` (que já foi usado por engano numa versão anterior: isso dava a média da ESPESSURA inteira, errado quando a espessura tem mais de um "Plano de Corte" com arranjos/tempos diferentes).
- **Sobras reais** (`nestingUtils.js::calcularSobrasAproveitaveis`): algoritmo de retângulos livres estilo "guillotine" — parte da área útil da chapa, vai descontando cada peça posicionada (split em até 4 tiras por peça), filtra só retângulos com os dois lados **≥100x100mm**, remove os totalmente contidos em outro, e por fim faz uma seleção gulosa por área (maior primeiro, descartando qualquer candidato que ainda se sobreponha a um já aceito) — garante que a lista final NUNCA tem sobreposição entre si, ou seja, o mesmo pedaço físico de chapa nunca é reportado duas vezes. Regra de negócio (`nestingPdf.js::desenharPaginaDoPlano`): se `item.sobra_reservada_cliente` for `false`, nem calcula — mostra "A sobra ficará na empresa." Se for `true`, lista os retângulos encontrados (Medida/Quantidade×multiplicador da chapa/Peso Unitário/Peso Total, peso pela fórmula padrão área×espessura×densidade); se não achar nada ≥100x100, cai no texto "Nenhuma sobra aproveitável neste plano."
  - **Bug crítico já corrigido, não reintroduzir**: a poda de retângulos "contidos em outro" (`podarContidos`) precisa rodar A CADA placement processado, não só uma vez no final. ## Impressão do orçamento (`window.print`, tela "Resultado")

CSS em `App.css` (`@media print`). **Armadilha já resolvida uma vez, documentar pra não reabrir**: o tema escuro (`document.documentElement.classList.add('dark')`) usa CSS custom properties (`--text-heading`, `--surface-card` etc, redefinidas dentro do seletor `.dark`) que **não são removidas na impressão** — a media query `print` não tira classes do DOM. Um `body { background: white !important }` sozinho NÃO resolve, porque elementos com `background`/`color` próprios (`.surface-card`, `.surface-heading`, `.input-field`...) não herdam do `body`. A correção certa é redefinir as mesmas variáveis dentro de `@media print { .dark { ... valores claros ... } }`, garantindo que o PDF impresso sai sempre no padrão claro independente do tema ativo na tela.

## Convenções de código

- Backend e frontend são monólitos de um arquivo por design até agora — só extrair módulo novo (como `nesting.py`, ou os módulos de PDF do frontend) quando a lógica for autocontida o suficiente para não precisar ficar importando meio-a-meio com o arquivo principal.
- **Padrão de "template genérico x orquestrador específico"** (estabelecido com `relatorioIndustrialPdf.js` x `nestingPdf.js`): quando um pedaço de UI/documento é pensado pra ser reaproveitado fora do GeoQuote (outras ferramentas do nicho ferro/aço), ele vira um módulo que só conhece formas/dados genéricos (sem "peça"/"orçamento"/"nesting" no vocabulário), e um segundo módulo — esse sim GeoQuote-específico — monta os dados e chama o genérico em sequência. Repetir esse padrão se surgir outro documento/tela com a mesma vocação de virar padrão da empresa.
- Nomes de variáveis/labels em português (domínio de negócio brasileiro: impostos, chapas, furos etc.), nomes de infraestrutura (funções fetch, constantes) em português também, seguindo o padrão já estabelecido no arquivo.
- CRUD upsert pela chave natural (não por id) é o padrão em todas as rotas de cadastro — mantenha essa convenção em rotas novas.
- Peça DXF-importada carrega hoje até 3 blobs auxiliares no objeto client-side (`dxfPreviewSvg`, `contornoDxf`, e os campos escalares de área/perímetro) — nenhum deles vai pro backend em `/calcular-orcamento` (Pydantic ignora campos extras por padrão, então mandar não quebraria nada, mas também não teria efeito). Se um dia esses dados precisarem ser persistidos (histórico de orçamento salvo, por exemplo), isso vai exigir decidir onde armazenar — hoje eles só sobrevivem enquanto a aba do navegador está aberta.
